# MacMarkDown Development Guide

Welcome to the MacMarkDown project. MacMarkDown is a native macOS Markdown editor written from scratch in pure Swift and SwiftUI: macOS 26 and Swift 6.4 opened a new era for Apple's developer frameworks — SwiftUI, the Observation framework, TextKit 2 and Swift concurrency became mature enough to carry a complete writing tool.

This guide covers everything you need to get started developing, building, testing, and contributing to MacMarkDown.

---

## 1. Prerequisites

| Requirement | Minimum Version | Recommended |
|-------------|-----------------|-------------|
| macOS       | 26.0            | 26.0+       |
| Xcode       | 26.0            | 26.0+       |
| Swift       | 6.4             | 6.4+        |

You must have a valid Apple Developer account to download Xcode 26 from [developer.apple.com](https://developer.apple.com) or the Mac App Store.

Verify your toolchain:

```bash
swift --version        # Expected: swift-driver version 6.4.x
xcodebuild -version    # Expected: Xcode 26.0
```

## 2. Getting Started

### 2.1 Clone the Repository

```bash
git clone https://github.com/xAIat/MacMarkDown.git
cd MacMarkDown
```

### 2.2 Open the Project

```bash
open MacMarkDown.xcodeproj
```

> Open **`MacMarkDown.xcodeproj`** (the single Xcode project), not the
> repository folder. The project is generated from `project.yml` by XcodeGen
> and contains four targets: the `MacMarkDown` app, the `MacMarkDownKit`
> framework (core logic), the `MacMarkDownCLI` command-line tool (product
> `macmarkdown-cli`), and `MacMarkDownTests`.
> There is no `Package.swift` at the root — everything lives in the Xcode
> project. After changing `project.yml`, regenerate the project with
> `xcodegen generate`.

### 2.3 Resolve Dependencies

Xcode will automatically resolve Swift Package Manager dependencies
(`swift-markdown` and `Yams`) on first open. If not, run:

```bash
xcodebuild -project MacMarkDown.xcodeproj -scheme MacMarkDown -resolvePackageDependencies
```

Or in Xcode: **File → Packages → Resolve Package Versions**.

## 3. Building

### 3.1 Build with Keyboard Shortcuts

| Action       | Shortcut   |
|--------------|------------|
| Build        | `Cmd+B`    |
| Run          | `Cmd+R`    |
| Test         | `Cmd+U`    |
| Clean        | `Cmd+Shift+K` |
| Profile      | `Cmd+I`    |

### 3.2 Build from Command Line

```bash
# Debug build
xcodebuild -scheme MacMarkDown -configuration Debug build

# Release build
xcodebuild -scheme MacMarkDown -configuration Release build
```

`./scripts/build.sh [debug|release]` wraps the same command and writes its
products and log to `.derived/`.

> **Signing**: the project does not pin a development team. Select your own
> team under **Signing & Capabilities** before building, or build unsigned
> with `xcodebuild ... CODE_SIGNING_ALLOWED=NO`.

### 3.3 Build for Specific Architecture

```bash
# Apple Silicon
xcodebuild -scheme MacMarkDown -arch arm64 build

# Intel
xcodebuild -scheme MacMarkDown -arch x86_64 build

# Universal
xcodebuild -scheme MacMarkDown -arch "arm64 x86_64" build
```

The app is a first-class macOS document app: a custom TextKit 2 editor
(`MarkdownTextView`) sits beside a native SwiftUI preview, scroll sync is
driven by `ScrollSyncService`, and WKWebView is used only for the web-native
blocks — tables and TeX math in the live preview, plus Mermaid/Graphviz
diagrams in exported HTML. HTML/PDF export goes
through `Renderer` (with `Default.handlebars` and the `Styles/*.css`
stylesheets) and `ExportService`.

### 4.1 Version Control Conventions

| Path | Tracked | Notes |
|------|---------|-------|
| `Opencode/` | ❌ Ignored | Local model access config templates (`opencode.jsonc_*`, grouped by model/network); machine-local only, never committed. |
| `opencode.jsonc` | ❌ Ignored | The machine-local opencode config actually in effect (local models/ports); ignored in `.gitignore`. |
| `.derived/`, `build/`, `DerivedData/` | ❌ Ignored | xcodebuild products and caches; `.derived/` is produced by `scripts/*.sh` and can be regenerated at any time. |

## 5. Key Dependencies

| Package        | Version | Purpose                        |
|----------------|---------|--------------------------------|
| `swift-markdown` | 0.6+  | Apple's Markdown parser (AST)  |
| `Yams`         | 5.0+    | YAML parsing for front matter  |

`swift-cmark`, the C parser underneath `swift-markdown`, arrives transitively
and is not declared directly. These packages are declared in `project.yml`
(Xcode package dependency) and resolved by Xcode. No other external
dependencies are used by default.

### Adding a New Dependency

1. Open `project.yml`.
2. Add the package to the `packages` map.
3. Add it as a target dependency under the appropriate target.
4. Run `xcodegen generate`, then **File → Packages → Resolve Package Versions**.

## 6. Adding New Markdown Extensions

MacMarkDown builds on Apple's `swift-markdown` and extends it in two layers:
preprocessing passes in `MarkdownParser` that rewrite source before parsing,
and a flag in `MarkdownParseOptions` that switches the pass on. New syntax
should always go through those layers so the editor, the native preview and
the HTML exporter stay in agreement.

### Step-by-Step

1. **Add a parse option** in `MacMarkDown/Markdown/MarkdownElement.swift`:

```swift
public struct MarkdownParseOptions: Sendable, Hashable {
    // …
    public var enableMyExtension: Bool
}
```

2. **Implement the syntax pass** in
   `MacMarkDown/Markdown/MarkdownParser.swift`. Preprocess the source before
   `Document(parsing:options:)`, and use `transformOutsideFencedCode(_:_:)` so
   fenced code blocks are never rewritten:

```swift
if options.enableMyExtension {
    body = Self.transformOutsideFencedCode(body) { segment in
        applyMyMarker(to: segment)   // line-preserving rewrite
    }
}
```

   For inline syntax, follow the sentinel pattern in
   `applyInlineExtensionMarkers` (used by underline, highlight and
   superscript): bracket the run with private-use markers, then map the pair
   to a new `InlineElement` case in `convertInlines`.

3. **Render the new element** in
   `MacMarkDown/Services/Preview/AttributedRenderer.swift` (native preview)
   and `MacMarkDown/Services/Preview/Renderer.swift` (HTML export); add the
   corresponding case to `MacMarkDown/UI/Shared/Preview/MarkdownView.swift`
   when the preview is rendered as SwiftUI views.

4. **Expose the option** if users should control it: add a property to
   `MacMarkDown/Stores/Preferences.swift`, a toggle in the **Markdown** pane of
   `MacMarkDown/UI/Shared/Settings/SettingsView.swift`, and pass the value
   through `Preferences.parseOptions`.

5. **Add tests** in `MacMarkDown/Tests/MarkdownParserTests.swift`, plus
   `AttributedRendererTests.swift` or `PreviewRenderingTests.swift` for
   rendering coverage.

6. **Update documentation** — add the extension to this guide in both EN and ZH.

## 7. Adding New Themes

MacMarkDown has two theme systems: preview themes (`Theme` values in
`MacMarkDown/Theme/Theme.swift`, backed by a CSS stylesheet for export) and
editor themes (`EditorTheme` values plus INI-like `.style` files). Keep the
theme name consistent across all three artifacts.

### Step-by-Step

1. **Create the export stylesheet** `MacMarkDown/Resources/Styles/My Theme.css`.
   `Renderer` and `TablePreviewHTML` look it up by the theme's `displayName`
   or `name` through `ResourceLoader.styleSheet(forTheme:)`, and fall back to
   styles generated from the `Theme` palette when no file matches.

2. **Define the preview theme** in `MacMarkDown/Theme/Theme.swift`:

```swift
public static let myTheme = Theme(
    name: "My Theme",
    displayName: "My Theme",
    backgroundColor: Color(red: 1.0, green: 1.0, blue: 1.0)
    // …the remaining palette colors
)
```

3. **Register the theme** in `Theme.all` so it appears in
   **Settings → HTML → Preview Style**:

```swift
public static let all: [Theme] = [
    clearness, github, solarizedLight, solarizedDark, night, myTheme
]
```

4. **For an editor theme**, either add an `EditorTheme` value in
   `MacMarkDown/Theme/EditorTheme.swift` and append it to `EditorTheme.all`,
   or drop a `.style` file into `MacMarkDown/Resources/Themes/` — bundled
   files are discovered automatically by `EditorTheme.fileBased`
   (`EditorTheme+StyleFile.swift`).

5. **Test** by selecting the theme in **Settings → HTML** (preview style) or
   **Settings → Editor** (editor style), and add coverage in
   `MacMarkDown/Tests/EditorThemeStyleFileTests.swift` and
   `MacMarkDown/Tests/PreviewRenderingTests.swift`.

## 8. Running Tests

The `MacMarkDownTests` target uses XCTest. Test files live directly under
`MacMarkDown/Tests/`, one file per area.

### 8.1 Run All Tests

In Xcode: `Cmd+U`

From command line:

```bash
xcodebuild test -scheme MacMarkDown -destination "platform=macOS"
```

Or `./scripts/test.sh` (add `--coverage` for a coverage result bundle).

### 8.2 Run Specific Test Suites

```bash
# Formatting and operations
xcodebuild test -scheme MacMarkDown \
    -only-testing:MacMarkDownTests/EditorFormattingTests

# Parsing
xcodebuild test -scheme MacMarkDown \
    -only-testing:MacMarkDownTests/MarkdownParserTests

# Native preview rendering
xcodebuild test -scheme MacMarkDown \
    -only-testing:MacMarkDownTests/AttributedRendererTests
```

### 8.3 Run Tests in Parallel

```bash
xcodebuild test -scheme MacMarkDown -parallel-testing-enabled YES
```

### 8.4 Generate Code Coverage

```bash
xcodebuild test -scheme MacMarkDown -enableCodeCoverage YES \
    -derivedDataPath ./DerivedData
```

View the coverage report in Xcode via **Report Navigator → Coverage**.

## 9. Debugging Tips

- **Editor state inspection**: set breakpoints in
  `MacMarkDown/UI/macOS/Editor/MarkdownTextView/MarkdownTextView.swift` or
  `MacMarkDown/UI/Shared/Document/DocumentView.swift` to inspect the text
  buffer, selection and undo stack.
- **Preview debugging**: the live preview is native SwiftUI + TextKit 2
  (`MarkdownView`, `MarkdownPreviewSurface`); only tables, math and diagram
  blocks use WKWebView, so enable **Develop → MacMarkDown** in Safari to
  inspect those web blocks.
- **Concurrency issues**: Use the Thread Sanitizer (**Scheme → Diagnostics → Thread Sanitizer**) to catch data races.
- **Performance**: Use Instruments with the **Time Profiler** template to identify hot paths.

## 10. Common Tasks

### Adding a New Keyboard Shortcut

1. Add the case to `EditorFormatCommand` and handle it in
   `EditorFormatting.apply`
   (`MacMarkDown/Services/Editor/EditorFormatting.swift`); the text
   transformation itself goes in `EditorOperations.swift`.
2. Add a menu item with `.keyboardShortcut` to the Format `CommandMenu` (or
   the relevant `CommandGroup`) in
   `MacMarkDown/Application/MacMarkDownApp.swift`.
3. Route the command to the front window through the existing notification
   pattern (`Constants.formatCommandUserInfoKey`); `DocumentView` applies it to
   the editor's selection. Add it to `ToolbarView` too if it should be
   discoverable.
4. Add tests in `MacMarkDown/Tests/EditorFormattingTests.swift` and
   `EditorOperationsTests.swift`.
5. Update the keyboard shortcuts table in documentation.

### Adding a New Preference

1. Add the property to the matching section of
   `MacMarkDown/Stores/Preferences.swift`, add its `Key` case, and seed the
   default in `init` so the setter persists it to `UserDefaults`.
2. Add the UI control to the matching pane in
   `MacMarkDown/UI/Shared/Settings/SettingsView.swift` (General, Markdown,
   Editor, HTML or Terminal).
3. If the preference affects parsing or export, thread it through
   `Preferences.parseOptions` so `MarkdownParser` and `Renderer` see it.
4. Add a test in `MacMarkDown/Tests/PreferencesTests.swift`.

The class is `@MainActor @Observable`, so bound controls refresh automatically
when a preference changes.

### Fixing a Bug

1. Write a failing test that reproduces the bug.
2. Fix the bug in the source code.
3. Verify the test passes.
4. Run the full test suite to check for regressions.

## 11. CI/CD

The project keeps its checks in `scripts/` so the exact same commands run
locally and in CI:

- `./scripts/build.sh [debug|release]` — build verification into `.derived/`.
- `./scripts/lint.sh` — strict-concurrency warnings, TODO/FIXME markers, file
  structure and TextKit 2 compliance.
- `./scripts/test.sh [--coverage]` — unit tests, optionally with a coverage
  result bundle.

A typical pipeline runs build, lint and test on every push and on every pull
request to `main`, and publishes the coverage report from `test.sh
--coverage`. Point your CI provider (for example GitHub Actions) at these
scripts; no workflow files are checked into the repository.
